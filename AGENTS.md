# AGENTS.md

## Projekt

LeanChat — schlanker Chat für OpenAI-kompatible Endpunkte (FastAPI-Backend,
verschlüsselte per-user SQLite-Dateien, statisches ES-Module-Frontend ohne Build-Schritt).

## Wichtige Dokumente

- [README.md](README.md) — Architektur, Features, Speicherlayout
- [SPEC.md](SPEC.md) — fachliche Spezifikation
- [docs/rootless_install.md](docs/rootless_install.md) — Playwright/Chromium rootless installieren und die e2e-GUI-Tests (`pytest -m e2e tests/e2e`) ohne root ausführen
- [docs/e2e_real_llm.md](docs/e2e_real_llm.md) — denselben User-Journey-e2e-Test manuell gegen ein echtes LLM laufen lassen (Opt-in via `LEANCHAT_E2E_REAL_LLM=1`, nie automatisch)

## UI-Testbarkeit

Alle UI-Elemente tragen ein eindeutiges `data-testid` (dynamische Elemente mit
id-suffix, z. B. `session-tile-<id>`, `bubble-msg-<id>`). e2e-Tests sollen
ausschließlich diese Selektoren verwenden.


## Testing

- `npm test` — JS-Unit-Tests (node:test)
- `python3 -m pytest` — Python-Unit-Tests (e2e per Marker deselektiert)
- `python3 -m pytest -m e2e tests/e2e` — GUI-Tests mit Playwright gegen Mock-LLM (braucht Chromium, siehe docs/rootless_install.md); gegen echtes LLM siehe docs/e2e_real_llm.md. e2e-Tests pruefen serverseitige Persistenz **nur ueber die oeffentliche API** (`GET /api/sessions/{id}` etc.) — nie direkt in `<data_dir>/users/*.db.enc` lesen/entschluesseln, damit die Persistenzschicht austauschbar bleibt (Verschluesselung at rest wird von `tests/test_encryption_at_rest.py` abgedeckt).
- `python3 -m ruff check app tests` — Lint (Regel-Set in pyproject.toml, CI-Job `lint`)
- `python3 -m mypy` — Typecheck (strict, Konfig in pyproject.toml `[tool.mypy]`, CI-Job `typecheck`); `app/`, `scripts/` und die Root-`main.py` sind vollstaendig typisiert
- Alle Suiten vor jedem Push laufen lassen: `python3 -m pytest`, `npm test`, `python3 -m ruff check app tests` und `python3 -m mypy`.

## Rules for contributors

1. **DB-Zugriff in Produktionscode nur ueber das Persistenz-Gateway `app/services/store.py`** (Schnittstelle `UserStoreProtocol`; Implementierung `SqliteUserStore`; `InMemoryUserStore` nur fuer Tests). Router und MessageService rufen asynchrone, fachliche Methoden und bekommen Domain-Models (`app/domain.py`) — weder `sqlite3.Connection` noch Datei-/Verschluesselungs-Details. `Database.user_db` + die `q_*`-Helper aus `app/db/database.py` benutzt nur der Store selbst (plus die DB-Unit-Tests). Jede Store-Methode oeffnet die per-user DB genau einmal und kapselt `asyncio.to_thread`.
2. **Jeder `/api/*`-Endpunkt braucht `Depends(get_current_user)`** (Ausnahmen: `/api/meta`, `/api/auth/config`). Auto-Login (`LEANCHAT_AUTO_LOGIN=1`) ist nur mit Loopback-Host erlaubt — nie in Produktion.
3. **MessageService als Single Write Funnel (`app/services/chat.py`):** `POST /api/chat` startet eine Hintergrund-Task im MessageService, der pro heisser Session den vollen In-Memory-Zustand haelt (`_SessionState`: Message-Liste + seq + Lock + SSE-Subscriber + laufende Generierung). **Jede Mutation wird zuerst auf die In-Memory-Messages ausgefuehrt (unter dem per-session Lock), dann via Store persistiert (write-through: die HTTP-Antwort kommt erst nach erfolgreichem Schreiben), dann als versioniertes SSE-Event (`state` mit seq) publiziert** — bei Persist-Fehler Rollback des Memory. Die Datenbank ist 'truth at rest': beim ersten Touch wird der Hot-State aus dem Store geladen (`_hot`), nach `LEANCHAT_HOT_SESSION_TTL_S` ohne Aktivitaet evictiert (nie bei laufender Generierung/Subscribern). Das Frontend bekommt Live-Daten ausschliesslich per SSE (`GET /api/chat/stream/{sid}`: `state`/`done`/`idle`) und pollt zusaetzlich `GET /api/sessions/{id}` (Poll = Quelle der Wahrheit fuer den persistierten Stand, ueberschreibt den SSE-Stand). **Persistenz-Regel (Performance):** die per-user DB wird nicht pro Chunk entschluesselt — abgeschlossene Stream-Bloecke (Typwechsel/Stream-Ende) werden blockweise persistiert (ein DB-Oeffnen pro Block-Abschluss plus ein finales); der offene Block bleibt als Live-Message (id=null) im Memory und wird bei Abort/Fehler verworfen (aus dem Memory entfernt, nie geschrieben). `messages.created_at` ist ms und traegt pro Block den Abschluss-Zeitstempel. Ein `tool_results`-Item mit `signal`-Feld ist ein reines Signal des LLM-Servers (schliesst den offenen Block, legt aber keine Zeile an). Der Upstream-Stream wird vor der Persistenz nie gefiltert: Anzeige-Settings (`show_reasoning`/`show_tool_output`) wirken clientseitig (`visibility.js`) — sonst wuerden Tool-Ergebnisse bei abgewaehlter Anzeige nie in die DB gelangen und beim Wiedereinblenden fehlen. Starke Referenzen auf Tasks halten (`MessageService._tasks`). `POST /api/chat` setzt das `generating`-Flag atomar unter dem per-session Lock im Service (`start_generation` -> `try_start_generating`); ein verwaistes Flag (z. B. Server-Neustart mitten in der Generierung) wird dort geheilt, statt dauerhaft 409 zu liefern. `POST /api/chat/abort` setzt das Abort-Event des Service (`request_abort`), das gegen Response-Open und jeden Chunk-Read geracet wird; der Abort-Endpoint setzt `generating` auf 0, wenn keine Task laeuft (verwaistes Flag), sonst setzt der finale Flush das Flag. Der Client zeigt den Abbrechen-Button, solange die aktive Session `generating=1` meldet (auch nach Reload). **Chat-History:** serverseitig aus der Session-DB via `build_llm_context` (`app/services/context.py`) — Toolcalls als `assistant`-`tool_calls`, Tool-Ergebnisse als gepaarte `tool`-Messages; `in_context=false` wird ausgespart. Alle Toolcalls einer Gruppe (z. B. parallele Toolcalls eines Deep-Research-Schritts) landen in einem einzigen `assistant`-Message direkt gefolgt von ihren `tool`-Messages; unvollstaendige Paare (Toolcall ohne Toolresult) werden ganz verworfen, damit das Request gegenueber strikten LLM-Servern gueltig bleibt (sonst 422 bzw. das Modell sieht die Tool-Ergebnisse nicht). Dabei werden zwei weitere 422-Fallen strikter Server vermieden: reine tool_call-Messages senden `content: ""` (leerer String statt null/fehlendem Feld - passiert jedes Pydantic-Modell) und die tool_calls werden in eine unmittelbar vorausgehende assistant-Content-Message gemerged (keine zwei `assistant`-Messages hintereinander). Whitespace-only-`system_prompt` wird nicht gesendet (sonst 422), und eine Session-System-Message mit identischem Text wie der Settings-Prompt wird nicht doppelt gesendet (UI rendert die Prompt-Bubble likewise nur einmal).
4. **SSE nur ueber `app/services/sse.py`**: Parsing via `parse_sse_data`/`parse_sse_buffer` (bzw. `SseParser`), Serialisieren ausgehender Events via `sse_event` — keine eigene `data:`-Logik duplizieren.
5. **Datei-Uploads per Multipart** (`UploadFile` in `app/routers/sessions.py`, `FormData` via `api.postForm` im Client); Verarbeitung serverseitig in `app/services/files.py`.
6. **Jedes interaktive UI-Element traegt ein eindeutiges `data-testid`** (kebab-case, `<element>-<context>[-<id>]`); e2e-Tests Adressieren Elemente ausschliesslich ueber diese Selektoren. Test-Aenderungen landen im selben Commit.
7. **Frontend ohne Build-Schritt:** vanilla ES-Module in `static/js/`. Vor dem Einfuegen in `innerHTML` immer `esc()` aus `util.js` verwenden; clientseitig gerenderte Inhalte nur als Diff/Keyed-Update (siehe `renderChat` in `chat.js`).
8. **Secrets nie committen und nicht at rest persistieren:** Server-Secret nur via `LEANCHAT_SECRET`/`.secret`-Datei; die `app_config.json` enthaelt keine Secrets (`AppConfig.to_dict` filtert sie heraus). Per-user DB-Schluessel werden per Argon2id mit pro-User-Salt aus `app/auth.py:user_identity` abgeleitet; bestehende DBs migrieren ueber `legacy_key` automatisch.
9. **Dokumentation im selben Commit aktualisieren:** Aenderungen an Architektur, Endpunkten oder Startbefehlen ziehen Updates in `AGENTS.md`/`README.md`/`SPEC.md` nach — Doc-Drift ist der teuerste Wartungsfehler.
10. **Keep the separation between AGENTS.md and README.md clear.** AGENTS.md is for coding agents and contains technical information and guidelines. README.md shall contain human readable information about the project, about setting up the environment and how to use the app.
11. **SSRF-Schutz:** User-gesteuerte LLM-URLs (Settings + Chat) werden vor jedem Upstream-Request per `validate_llm_base_url` (`app/services/ssrf.py`, Klasse `LlmUrlValidator`) geprueft: nur http/https ohne Credentials; private/Loopback-/Link-Local-/reservierte Ziele sind blockiert, sofern der Server nicht auf Loopback bindet oder `LEANCHAT_ALLOW_PRIVATE_LLM=1` gesetzt ist (`AppConfig.allow_private_llm`). Der DNS-Lookup ist blockierend und in async-Kontexten via `asyncio.to_thread` aufzurufen. Upstream-Fehler-Bodies werden nie an den Client weitergereicht (nur Statuscode).
12. **DoS-Limits:** Uploads werden gestreamt mit Byte-Cap gelesen (`read_upload_capped` in `app/services/files.py`, 413 bei Ueberschreitung), dazu per-user Attachment-Kontingent (`q_total_attachment_bytes`) und globales Request-Size-Limit fuer `/api/*` (Middleware in `app/main.py`). Alle Limits sind Env-Variablen in der `AppConfig` und in `env-example` dokumentiert. Security-Header (CSP, nosniff, DENY, HSTS bei TLS) setzt die Middleware in `app/main.py`; nicht-API Antworten (statische ES-Module, Auth-Seiten) bekommen zusaetzlich `Cache-Control: no-cache`, damit Browser nach einem Deploy revalidieren statt alte/neue Module zu mischen (sonst schlaegt das Linken des Modul-Graphen fehl); das Session-Cookie bekommt `Secure` nur bei TLS (`app/auth.py`).
13. **Kommentare erklaeren nur das Warum, nie das Was** (Clean Code / Zen of Python / XP: der Code ist die beste Doku). Was-Kommentare, die den Code bloss wiederholen, divergieren bei Aenderungen und werden konsequent entfernt; nur nicht-offensichtliche Gruende, invarianten oder Fallstricke (z. B. "lokal halten, sonst faellt der WeakValue-Eintrag vor Block-Ende weg") bleiben als knapper Einzeiler stehen. Namen so waehlen, dass sie die Intention tragen.
14. **Neue Umgebungsvariable landet im selben Commit in `env-example`:** Jede neu eingelesene Env-Variable (`os.environ`/`getenv` in `app/` oder in einem vendored Wheel, z. B. `USER_REGISTRY_SECRET_KEY`) wird in `env-example` dokumentiert (kurzer Kommentar + Default; Secrets nur als leerer Platzhalter; die Datei heisst bewusst nicht `.env.example`, damit `.env*`-Gitignore-Regeln sie nicht aus Versehen ignorieren). Ohne Eintrag in `env-example` existiert die Variable nicht. Gilt auch fuer Test-/E2E-Variablen (`LEANCHAT_E2E_*`, siehe `docs/e2e_real_llm.md`).
15. **Vollstaendig typisiertes Backend + Pydantic an den Grenzen:** `app/` ist unter `mypy --strict` fehlerfrei (CI-Job `typecheck`). Interne dict-foermige Daten (DB-Zeilen, User-Identitaet) sind TypedDicts in `app/types.py`; API-Requests/Responses sind Pydantic-Models (`app/models.py`), `AppConfig` ist ein Pydantic-Model mit Constraints (`app/config.py`) — Env-Werte und die persistierte `app_config.json` werden also validiert (`extra="forbid"` faengt Tippfehler in der JSON-Datei ab). Neue Felder/Funktionen immer mit Annotationen; `python3 -m mypy` muss gruen bleiben.
16. **Domain-Exceptions zentral mappen:** `SessionNotFound`/`MessageNotFound`/`AttachmentQuotaExceeded` (`app/services/store.py`), `UploadTooLarge` (`app/services/files.py`) und `VoiceServiceUnavailable`/`VoiceUpstreamError` (`app/services/voice.py`) werden einmalig in `create_app` (`app/main.py`) per `@app.exception_handler` auf HTTP-Status/Detail gemappt. Router und Services werfen die fachlichen Exceptions nur - kein lokales `except ...: raise HTTPException(...)` in Routern.
17. **Setting-Keys und Env-Mapping haben eine Single Source of Truth:** `BOOL_SETTINGS`/`STRING_SETTING_KEYS`/`CLEARABLE_WITH_EMPTY` in `app/services/settings.py`; `SettingsIn`/`SettingsOut` (`app/models.py`) werden dagegen per Import-Zeit-Assert geprueft, das Frontend (`static/js/settingsKeys.js`) per Test (`tests/test_settings_api.py`). `ENV_FIELD_SPEC` in `app/config.py` mappt die uebrigen Env-Variablen auf `AppConfig`-Felder; `tests/test_config.py` prueft, dass jede Variable in `env-example` dokumentiert ist.
